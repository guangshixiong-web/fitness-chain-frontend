# 项目运行全链路：从启动到退出，从头到尾讲一遍

> 项目：悦动健身连锁数据中控台（Next.js 16 前端框架教学项目）
> 启动：`npm run dev` → http://localhost:5173 ，演示账号 `admin` / `YueDong@123456`
> 一句话定位：**"只有前端、却像全栈"**——页面、状态、权限、接口、数据库全在一个 Next.js 工程里，后端是一个内存 Mock 层（`src/mock/`）。

## 0. 全局地图：一次请求的一生

```

  │                                          │
  ├─ 页面请求 ──────────────► proxy.ts（门卫，查 Cookie）
  │                                          │
  │                              (authenticated)/layout.tsx

  │                                          │

  │                              ◄── HTML + 预取数据 ────
  │                                          │
  ├─ 交互请求（点击/筛选）──► api.ts（axios）──► /api/v1/* route.ts

  │                                          └──────► handleMockApi ──► 内存 db
  │                                                    ▲
  │                              两条通道，同一个 Mock 后端┘
```

## 阶段一：启动项目时发生了什么

```powershell
npm run dev    # 实际执行 next dev -p 5173（见 package.json）
```

1. Next.js 16 开发服务器在 **5173 端口**启动，开始**按需编译**页面（哪个页面被访问才编译哪个，所以首次打开某页会慢一点，之后就快）；
2. **Mock 数据库初始化**：第一次有代码用到 `src/mock/db.ts` 时，它往 `globalThis.__yuedongFrontendMockDb` 里灌入种子数据——3 个账号、3 区域、4 门店、84 条订单、36 张会员卡、6 名教练、24 条预约、8 台器械、20 条巡检记录等。
   - 挂在 `globalThis` 上的原因：开发模式热更新会重新加载模块，挂全局变量才能**改代码不丢数据**；
   - **重启 dev 服务器 → 数据重置回种子**。这是教学项目的刻意设计。

> **大白话**：开店营业前，先把假账本、假会员、假器械全部摆好。你每天打烊（重启）后货架复原，但营业期间临时改个价（热更新）货架不动。

## 阶段二：浏览器打开 http://localhost:5173

**第一关：门卫 `proxy.ts`（项目根目录，第 5-22 行）**

```ts
const publicPaths = new Set(['/login', '/help', '/status'])

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl
  const hasSession = request.cookies.has('yuedong_session')
  if (!hasSession && !publicPaths.has(pathname)) {
    return NextResponse.redirect(new URL('/login', request.url))
  }
  if (hasSession && pathname === '/login') {
    return NextResponse.redirect(new URL('/dashboard', request.url))
  }
  return NextResponse.next()
}
export const config = { matcher: ['/((?!api|_next/static|_next/image|favicon.ico).*)'] }
```

### 逐行讲解

| 行 | 含义 | 为什么这么写 |
|---|---|---|
| `const publicPaths = new Set(...)` | 定义"无需登录就能访问"的公开页面白名单 | 用 Set 而非数组，`has()` 查找是 O(1)；集中管理便于以后加新页面 |
| `function proxy(request)` | Next.js 16 的**门卫函数**（原 middleware），每个匹配的请求都会先经过它 | 在渲染之前执行，是最轻量的"前置过滤器" |
| `const { pathname } = request.nextUrl` | 解构出当前请求的路径，比如 `/dashboard` | 后面要用它判断"访问的是哪个页面" |
| `const hasSession = request.cookies.has('yuedong_session')` | 检查浏览器有没有带登录 Cookie | 只查"存不存在"，**不解析内容**——性能最优，但也意味着这关只防君子不防小人 |
| `if (!hasSession && !publicPaths.has(pathname))` | 既没登录、又不是公开页面 | 两个条件都满足才拦，保证 `/login` `/help` `/status` 不会被自己卡死 |
| `return NextResponse.redirect(new URL('/login', request.url))` | 重定向到登录页 | 用 `request.url` 拼出新 URL，保留当前协议和主机，避免硬编码域名 |
| `if (hasSession && pathname === '/login')` | 已经登录了却还想访问登录页 | 已登录用户没必要再看登录页，直接送进系统 |
| `return NextResponse.redirect(new URL('/dashboard', ...))` | 重定向到经营总览 | 已登录用户的默认落地页 |
| `return NextResponse.next()` | 放行，让请求继续往下走（进入页面渲染） | 没命中拦截条件就正常通过 |
| `matcher: ['/((?!...).*)']` | 正则排除 API、静态资源、favicon | 这些请求不需要走认证逻辑，排除掉可以减少无谓执行，也避免影响静态资源加载 |

> 注意：它只查"有没有 Cookie"，**不查真假**——伪造一个 Cookie 也能骗过这关，所以后面还有真认证。

## 阶段三：登录——领门禁卡

**1. 登录页渲染**：`app/login/page.tsx` 用 `Provider` 包住 `src/views/login.tsx`（客户端组件），页面上有演示账号提示。

**2. 提交表单**（`src/views/login.tsx` 第 40-55 行）：

```tsx
const submit = async (e: React.FormEvent) => {
  e.preventDefault()
  if (loading) return
  setLoading(true)
  try {
    await api.post('/auth/login', { username, password })
    await dispatch(loadMe())
    toast({ title: '登录成功', description: '欢迎回来，今天也要全力以练', variant: 'success' })
    router.replace('/dashboard')
    router.refresh()
  } catch (err) {
    toast({ title: '登录失败', description: errorMessage(err), variant: 'error' })
  } finally {
    setLoading(false)
  }
}
```

### 逐行讲解

| 行 | 含义 | 为什么这么写 |
|---|---|---|
| `async (e: React.FormEvent)` | 异步事件处理函数，接收表单提交事件 | 内部有 await，必须声明 async |
| `e.preventDefault()` | 阻止浏览器表单的默认提交行为 | 默认提交会整页刷新、URL 变成 `?username=...&password=...`（密码暴露在地址栏），必须拦截 |
| `if (loading) return` | 如果正在请求中，直接返回 | 防止用户连点按钮发多次登录请求（防抖） |
| `setLoading(true)` | 把按钮置为 loading 状态 | 配合 `<Button disabled={loading}>` 让按钮变灰、文字变"登录中…"，给用户明确反馈 |
| `await api.post('/auth/login', { username, password })` | 调全局 axios 发登录请求 | 后端校验账号密码，**成功后在响应头写入 `yuedong_session` Cookie**。注意这一步只发卡，不返回用户数据 |
| `await dispatch(loadMe())` | 派发 Redux thunk，再调一次 `/auth/me` | 登录接口只发卡，不返回用户详情；`loadMe` 用刚拿到的 Cookie 换出用户信息（姓名、角色、权限码），灌进 Redux |
| `toast({ title: '登录成功', ... })` | 右上角弹成功提示 | 即时反馈，不让用户以为卡住了 |
| `router.replace('/dashboard')` | 跳转到经营总览 | 用 `replace` 而非 `push`——**登录页不进浏览器历史**，登录成功后按返回键不会回到登录页 |
| `router.refresh()` | 强制 Next.js 重新渲染服务端组件 | 关键一步！`(authenticated)/layout.tsx` 会重新执行 `loadAuthenticatedUser()`，把最新用户注入 Provider，确保首屏就拿到正确权限 |
| `catch (err)` | 捕获请求失败 | 失败可能是网络错误或后端返回 401 |
| `errorMessage(err)` | 从错误响应里提取后端返回的文案 | `api.ts` 里的辅助函数，统一解析 `{ code, message }` 信封，避免每个页面自己写解析逻辑 |
| `finally { setLoading(false) }` | 无论成功失败，恢复按钮状态 | 用 `finally` 保证一定执行；如果只在 try/catch 里写，万一抛异常没被 catch 到按钮会一直卡着 |

**3. 统一传话窗口**（`src/lib/api.ts` 第 6-19 行）：全项目唯一的 axios 实例，地址前缀 `/api/v1`，`withCredentials` 保证带 Cookie；响应拦截器统一处理 401——**任何请求发现会话过期，自动跳回登录页**。

| 行 | 含义 | 为什么这么写 |
|---|---|---|
| `axios.create({ baseURL: '/api/v1', ... })` | 创建唯一 axios 实例 | 全项目共用一个实例，配置统一；不用到处 `import axios` 再配一遍 |
| `timeout: 15000` | 15 秒超时 | 防止请求无限挂起 |
| `withCredentials: true` | 跨域时也带 Cookie | 即使后端在别的域名，Cookie 也能带上 |
| `if (status === 401 && !endsWith('/login'))` | 会话过期且不在登录页 | 在登录页本身 401 不能跳，否则死循环 |
| `window.location.href = '/login'` | 硬跳转登录页 | 用 `window.location` 而非 router，确保整页刷新、清掉旧状态 |

**4. 传达室**（`app/api/v1/[...path]/route.ts`）：catch-all 路由接住 `/api/v1/auth/login`，把 HTTP 请求翻译成函数调用交给 Mock 后端，自己零业务逻辑；返回时把 Mock 层要求的 Cookie 翻译成真实的 `Set-Cookie` 写回浏览器。

**5. 真正办事的后台**（`src/mock/handlers.ts` 第 340-354 行）：

```ts
if (root === 'auth' && second === 'login' && method === 'POST') {
  const body = asRecord(request.body)
  const user = db.users.find((u) => u.username === username && u.enabled)
  if (!user || user.password !== password) {
    addLog(db, null, 'auth', 'login', false)
    return fail(401, '用户名或密码错误')
  }
  addLog(db, user.id, 'auth', 'login', true)
  return ok(
    { accessToken: `mock:${user.id}` },
    { type: 'set', name: SESSION_COOKIE, value: `mock:${user.id}`, maxAge: 60 * 60 * 8 },
  )
}
```

### 逐行讲解

| 行 | 含义 | 为什么这么写 |
|---|---|---|
| `if (root === 'auth' && second === 'login' && method === 'POST')` | 匹配 `POST /auth/login` | `root`/`second` 是按 `/` 切出来的路径段，用三段判断定位具体接口 |
| `const body = asRecord(request.body)` | 把请求体转成普通对象 | `body` 可能是各种类型，`asRecord` 兜底保证至少是 `{}` |
| `db.users.find((u) => u.username === username && u.enabled)` | 在内存用户表里找**启用状态**的同名用户 | 多了 `u.enabled` 条件——停用账号即使密码对也登不上 |
| `if (!user \|\| user.password !== password)` | 没找到用户，或密码不对 | 用 `\|\|` 合并两个失败条件，减少嵌套 |
| `addLog(db, null, 'auth', 'login', false)` | 失败也记一条操作日志，userId 为 null | 安全审计需要：谁在什么时候尝试登录失败，都要留痕 |
| `return fail(401, '用户名或密码错误')` | 返回 401 统一提示 | 不区分"用户不存在"和"密码错误"，避免攻击者通过错误信息枚举账号 |
| `addLog(db, user.id, 'auth', 'login', true)` | 成功登录记日志，带用户 ID | 便于追查"谁在什么时间登录过" |
| `return ok({ accessToken: ... }, cookie)` | 返回成功响应 + 一个 Cookie 动作描述 | 这是本项目的设计：Mock 层不直接写 Cookie，而是返回"动作描述"，由 route.ts 翻译成真正的 `Set-Cookie`。这样 Mock 层可以脱离 HTTP 环境独立测试 |
| `value: \`mock:${user.id}\`` | Cookie 值就是"mock:用户ID" | 教学简化版会话凭证，后续 `/auth/me` 用正则解析出用户 ID |
| `maxAge: 60 * 60 * 8` | 8 小时有效期 | 超过自动失效，需要重新登录 |

核对账号密码 → 发卡（`yuedong_session=mock:用户ID`，8 小时）→ 记一条操作日志（系统管理-操作日志页可见）。

**6. `loadMe()`**：调 `/auth/me`（handlers 第 362-366 行），从 Cookie 解析出用户，返回**用户 + 权限码列表**，灌进 Redux。

## 阶段四：进入经营总览——进楼、验卡、上菜

**1. 再过门卫**：这次有 Cookie 了，proxy 放行 `/dashboard`。

**2. 楼层管家真验卡**（`app/(authenticated)/layout.tsx` 第 7-16 行）：

```tsx
export default async function AuthenticatedLayout({ children }: { children: ReactNode }) {
  const user = await loadAuthenticatedUser()
  if (!user) redirect('/login')
  return (
    <Provider user={user}>
      <AppShell>{children}</AppShell>
    </Provider>
  )
}
```

### 逐行讲解

| 行 | 含义 | 为什么这么写 |
|---|---|---|
| `async function AuthenticatedLayout` | 这是**服务端组件**（Next.js 16 App Router 默认服务端），所以可以直接 await | 服务端组件在服务器上执行，能直接读 Cookie、调数据库，不暴露给浏览器 |
| `{ children }: { children: ReactNode }` | 接收子页面作为参数 | layout 包裹组内所有页面，children 就是当前页 |
| `const user = await loadAuthenticatedUser()` | 拿 Cookie 去 Mock 后端**真查一次** | proxy 只查"有没有卡"，这里才查"卡对不对"——防伪造 |
| `if (!user) redirect('/login')` | 查不到用户就踢回登录页 | 假卡/过期卡/已停用账号，全部拦住 |
| `<Provider user={user}>` | 把服务端查到的用户注入 Redux | `store.ts` 里 `makeStore(user)` 把 user 作为 `preloadedState`，客户端 hydration 后立刻可用，不用再请求 |
| `<AppShell>` | 渲染通用外壳（侧边栏、顶栏、用户菜单） | 所有登录后页面共享，不用每页重复写 |
| `{children}` | 渲染当前具体页面 | 被包在外壳里，统一布局 |

`(authenticated)` 是**路由组**：URL 里不出现，但组内 16 个页面全部共享这个 layout——认证逻辑只写一遍，新增页面自动被保护。

**3. 状态接力**（`src/store/store.ts`）：`makeStore(user)` 把服务端查到的用户作为 `preloadedState` 塞进 Redux，页面 hydration 后 `useAppSelector` 立刻可用，不用再请求一次。

**4. 外壳渲染**（`src/components/app-shell.tsx`）：侧边栏菜单在第 54-103 行定义，每项带权限码，第 182 行按 `user.permissions` 过滤——**你只能看到你有权限的菜单**。

**5. 薄页面预取数据**（`app/(authenticated)/dashboard/page.tsx` 第 12-25 行）：

```tsx
const [overviewResult, chartsResult] = await Promise.allSettled([
  serverApiFetch<Overview>('/metrics/overview'),
  serverApiFetch<Charts>('/metrics/charts'),
])
return (
  <PermissionBoundary code="dashboard:view">
    <DashboardView initialOverview={initialOverview} initialCharts={initialCharts} />
  </PermissionBoundary>
)
```

### 逐行讲解

| 行 | 含义 | 为什么这么写 |
|---|---|---|
| `await Promise.allSettled([...])` | 并行发起两个请求，**全部 settle 后才继续** | 比 `Promise.all` 好：一个失败不拖垮另一个（all 会在第一个 reject 时直接抛错） |
| `serverApiFetch<Overview>('/metrics/overview')` | 服务端直连 Mock 后端取统计卡数据 | 泛型 `<Overview>` 约束返回类型，TypeScript 编译期校验字段 |
| `const [overviewResult, chartsResult]` | 解构出两个结果对象 | 每个对象是 `{ status: 'fulfilled', value }` 或 `{ status: 'rejected', reason }` |
| `PermissionBoundary code="dashboard:view"` | 权限边界组件，检查是否有 `dashboard:view` 权限 | 防止直接输 URL 进入无权限页面 |
| `<DashboardView initialOverview={...} initialCharts={...} />` | 把预取数据作为 props 传给真正的视图组件 | "薄页面、厚视图"——page.tsx 只取数不画 UI，视图组件负责渲染 |

**6. 后厨内部对讲机**（`src/lib/api-server.ts` 第 20-51 行）：

```ts
export async function serverApiFetch<T>(path: string, init = {}): Promise<T> {
  const [pathname, query = ''] = path.split('?')
  let cookieHeader = (await getSessionCookieHeader()) || ''
  const result = handleMockApi({
    method: (init.method || 'GET').toUpperCase(),
    path: pathname,
    searchParams: new URLSearchParams(query),
    cookieHeader,
  })
  if (result.status >= 400) throw new ServerApiError(message, result.status)
  return (result.body as { data: T }).data
}
```

### 逐行讲解

| 行 | 含义 | 为什么这么写 |
|---|---|---|
| `export async function serverApiFetch<T>` | 服务端专用的取数函数，泛型 T 约束返回类型 | 带 `'server-only'` 标记，**编译期禁止客户端引用** |
| `path.split('?')` | 把 URL 拆成路径和查询串 | 如 `/orders?page=1` → `['/orders', 'page=1']` |
| `getSessionCookieHeader()` | 从当前请求读取 `yuedong_session` Cookie，拼成 header 字符串 | Mock 后端需要用它识别当前用户（鉴权 + 数据范围） |
| `handleMockApi({...})` | **直接函数调用** Mock 后端 | 不走 HTTP，不经过 route.ts——服务器自己请求自己太绕，直接调函数最快 |
| `method: (init.method \|\| 'GET').toUpperCase()` | 取请求方法，默认 GET，统一转大写 | handlers 里判断 `method === 'POST'` 时大小写敏感 |
| `searchParams: new URLSearchParams(query)` | 把查询串解析成标准 URLSearchParams | 统一格式，handlers 里用 `params.get('keyword')` 读取 |
| `if (result.status >= 400) throw new ServerApiError(...)` | 后端返回错误就抛异常 | 让 page.tsx 的 `allSettled` 能捕获，对应的数据传 null 兜底 |
| `return (result.body as { data: T }).data` | 从统一信封 `{ code, message, data }` 里取出 data | 所有接口都返回这个信封结构，客户端只关心 data 部分 |

**7. 客户端接管**（`src/hooks/use-api.ts`）：

```ts
export function useApi<T>(url: string, initialData: T | null = null) {
  const [data, setData] = useState<T | null>(initialData)
  const [loading, setLoading] = useState(initialData === null)
  const useInitialResponse = useRef(initialData !== null)
  useEffect(() => {
    if (useInitialResponse.current) {
      useInitialResponse.current = false
      return
    }
    void reload()
  }, [reload])
  return { data, loading, error, reload, setData }
}
```

### 逐行讲解

| 行 | 含义 | 为什么这么写 |
|---|---|---|
| `useState<T \| null>(initialData)` | data 初始值就是服务端预取的数据 | 有预取数据时，首屏直接渲染，不显示 loading |
| `useState(initialData === null)` | loading 初始值：有数据则 false，无则 true | 有预取数据就不转圈 |
| `useRef(initialData !== null)` | 用 ref 记录"是否有预取数据" | ref 不会触发重渲染，适合存"一次性标志位" |
| `useEffect(() => {...}, [reload])` | 组件挂载后执行副作用 | 首次渲染后决定要不要发请求 |
| `if (useInitialResponse.current) { ...; return }` | 如果有预取数据，**跳过第一次请求** | 服务端已经取过了，客户端不用重复取；把 ref 置 false，下次 URL 变化时会正常发请求 |
| `void reload()` | 触发重新请求 | `void` 是为了消除"未处理的 Promise"lint 警告 |
| `return { data, loading, error, reload, setData }` | 暴露状态和方法给组件 | `reload` 用于手动刷新，`setData` 用于乐观更新 |

`DashboardView` 里这样接预取数据：`useApi('/metrics/overview?...', initialOverview)`——有 initialData 就直接渲染**不转圈**，并跳过第一次请求。

> **大白话**：普通网站是你坐下再点菜、盯着空桌子等；这个项目是**你进门时菜已上桌**。

至此首屏完成：统计卡、图表全部有数据，无 loading。

## 阶段五：页面内交互——客户端通道

登录后的所有操作（筛选、增删改查、办卡、预约、巡检）都走同一条路：

```
视图组件 → api.get/post/patch → /api/v1/* → route.ts → handleMockApi → 内存 db → 响应 → useApi 更新界面
```

举例：**办一张会员卡**（`src/views/member-cards.tsx`）
1. 填表单点保存 → `api.post('/member-cards', {...})`；
2. handlers 校验字段 → `db.memberCards.unshift(...)` 写入内存库 → 记操作日志；
3. 前端 toast 提示成功 → `reload()` 重新拉列表 → 新卡出现。

再举例：**Dashboard 切换日期筛选**
1. 改日期 → URL 参数变化 → `useApi` 的 `reload` 触发；
2. 这次走**客户端通道**（axios → HTTP → route.ts → handlers）；
3. 统计口径在 handlers 的 `computeOverview/computeCharts` 里重算，返回新数据。

**关键认知**：首屏走"对讲机"（serverApiFetch 直连），交互走"传话窗口"（axios → HTTP），**但终点都是同一个 `handleMockApi`**——所以鉴权、数据范围过滤、业务规则只写一遍，两条通道都生效。

## 阶段六：权限是怎么层层生效的

以店长账号 `store.manager` 登录对比体验：

| 层 | 机制 | 效果 |
|---|---|---|
| 菜单 | app-shell.tsx 按权限码过滤 | 看不到"系统管理"等菜单 |
| 页面 | `PermissionBoundary` 检查权限码，无权限 `router.replace('/dashboard')` | 直接输 URL 也进不去 |
| 数据 | handlers 里 `filterStoreIds` 按数据范围过滤 | 总部看全部 / 区域经理看本区域 / 店长只看本店 |

权限码共 36 个（`db.ts` 种子），5 种角色通过 `permissionIds` 组合出不同能力。

## 阶段七：退出登录——还卡走人

1. 点右上角头像 → 退出登录；
2. `api.post('/auth/logout')` → handlers 返回"清除 Cookie"动作 → route.ts 删掉浏览器的 `yuedong_session`；
3. 前端 `clearAuth()` 清空 Redux → 跳回 `/login`；
4. 之后再访问任何页面 → proxy 一查：没卡 → 全部拦回登录页。

**常见疑问**：
